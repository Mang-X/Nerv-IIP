# Scope Gate：先定级，后动手

## 概览

级别决定交付形态，而不是干劲决定。每张 issue 在**建票时**和**实施前**各过一次定级；实施中命中升级触发器立即停下重判。判级看触发器，**不看代码量**。

## 分级与处理

| 级 | 特征 | 处理 |
|---|---|---|
| S | 单点修改、需求明确、低风险 | 直接实现，单 PR |
| M | 多文件但边界清晰 | 正常实现，单 PR；不夹带范围外改动 |
| L | 命中任一升级触发器 | **禁止直接实施**。先在票面写拆解清单（每个子项 ≤M、各自独立 PR 可审可绿），子项开子 issue 或票内 checklist；母票只跟踪，不承载代码 |
| XL | 架构变化、领域重构、大迁移 | 先出 Spec/ADR 独立评审（样板：ADR 0022 排程冻结、FileStorage #992），再拆多个 issue |
| ? | 不知道怎么做 | 开 Spike/Investigation 票并 timebox；产出=调查报告+重新定级的新票；spike 分支**不合并任何生产代码** |

## L 升级触发器（任一命中即 L）

1. 同时修改多个业务域；
2. 数据库模型 + API 契约 + UI 一起变（或触及 OpenAPI→gateway→codegen 两跳链、EF migration）；
3. 需要做架构决策；
4. 涉及兼容性 / 数据迁移；
5. 验收条件说不清；
6. 必须"读大量代码之后才能决定怎么做"；
7. 测试策略本身还不明确；
8. **账本/清单型任务**（"全仓 N 处""逐条登记逐条销"）——天然 L，实施=分层放血，每层一个 PR；
9. 触及 `.github/workflows`、治理门禁脚本、共享测试基建（错误爆炸半径是全仓）；
10. 预估单 PR 超过 ~15 个手写文件，或一个 diff 里混多种审核视角（信号项，结合判断）。

## 三道关卡

**Gate 1 · 建票时**：票面首段写级别与一行理由，打 `scope:S/M/L/XL/spike` 标签。一张票只装一个问题——手里是一份多发现清单时，按域/按层拆成多张票再提交，不开"大杂烩票"。

**Gate 2 · 实施前**：实施会话开工的**第一个动作**是在票或对话中复述：级别、交付形态（几个 PR、顺序、每个 PR 的独立验收）。与票面不符→先改票面再动手。L 级票面无拆解清单→**不开工**，退回拆解。

**Gate 3 · 实施中**：改动滚出票面范围（命中任一触发器）→ 停下，把膨胀部分开新票，本 PR 守住原范围。审核中发现的范围外问题同理（正例：#1510 六轮审核发现的三条全部另立 #1509/#1512，未搭车）。

## 合理化对照表

| 借口 | 事实 |
|---|---|
| "都是机械改动，一起做更快" | #1512 事故：23 个 commit、71 文件、+4439 行揉在一支未推送分支，审核无法下嘴，事后返工切成 6 层 |
| "拆开 PR 多付审核/构建成本" | 审核成本非线性：6 个可审的 PR 远快于 1 个不可审的巨 PR |
| "已经做完了，拆了浪费" | 成品可按路径重新装盘，但最便宜的时机是开工前 |
| "我记得要分层" | 记得≠落盘。级别与拆解必须写进票面——会话会中断、会换人 |
| "审核发现的顺手修了" | 审核发现的范围外问题=新票，否则 PR 永不收敛（#1510 曾六轮） |

## 红旗（出现即回到 Gate 重判)

- 开工数小时没有出第一个可审 PR；
- 工作分支落后 main 100+ commit 还未推送；
- commit 主题与票面标题对不上号；
- 想说"这个也该一起改"。
