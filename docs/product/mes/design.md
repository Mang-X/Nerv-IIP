## 1. 域定位（ISA-95）

MES（ISA-95 Level-3）分**四大运营域**：生产运营、质量运营、维护运营、库存运营；每域走**同一通用活动模式**：
`定义 → 资源管理 → 详细排程 → 派工 → 执行 → 数据采集 → 跟踪 → 分析`。

**本平台「制造执行」模块 ≈ 生产运营管理（Production Operations Management）。** 质量 / 设备 / 库存 / 需求计划是**独立域**（已有独立模块）。

**推论（硬约束）**：
- MES 模块的 IA 应**按生产运营活动流编排**，不按"管理动作"凑组。
- 质量、设备、库存的对象**不当 MES 主对象**；MES 内只保留它们的**只读窗口 / 跳链**，主维护在各自模块。

## 2. 目标 IA / 导航重构

### 2.1 现状问题（三视角共识）
1. **「异常与协同」是反模式杂物抽屉**：把产能(分析) / 规则排程(排程) / 班次交接(执行协同) / 质量·设备窗口(他域) 五个**弱关系实体硬凑**一组。
2. **同一 ISA-95 活动被物理打散**：生产计划 / 规则排程（都属排程）分居两组；在制跟踪 / 追溯（都属跟踪）分散。
3. **他域窗口被当 MES 主菜单项**：质量与不良、设备与停机占用 MES 顶层菜单，与独立「质量管理」「设备监控」模块认知冲突。
4. **同对象多视图被当独立页**：派工看板（工单的看板视图）、生产准备检查（开工 readiness 视图）各占一个菜单项。

### 2.0 命名原则（可发现性，硬约束）
> **导航 / 页面 / 按钮一律用一线操作动词**（领料 / 报工 / 派工 / 开工 / 完工 / 交接），让业务人员**一眼找到操作点、不靠翻文档**。
> ISA-95 的功能术语（执行准备 / 数据采集 / detailed scheduling）**只用于本设计文档的结构分组，不进界面**。**结构对齐 ISA-95，标签对齐一线话。**
> 反例（本文档 v1 踩坑）：用「执行准备」「报工采集」当组名 → 一线找不到「领料」；用「齐套与物料」当页名 → 藏掉了每天高频的「领料」操作。

### 2.2 目标导航树（结构按 ISA-95 活动流，标签用一线话）
```
制造执行（MES = 生产运营管理）          ← 括号内为 ISA-95 活动，仅说明，不上界面
├─ 生产总览        /mes                  [域首页 / Andon 总览]          (Analysis 总览)
├─ 计划与排程      生产计划 /mes/plans · 排程 /mes/schedules            (Scheduling)
├─ 工单与派工      /mes/work-orders[+详情]（派工看板收为页内 Tab）       (Dispatching)
├─ 领料与齐套      /mes/materials（开工准备 foundation 收为 Tab）         (Execution Readiness)
│                  ← 由「齐套与物料」改名，**领料**进标题；主操作=发起领料/领料申请
├─ 工序执行        工序执行 /mes/operation-tasks · 班次交接 /mes/handovers (Execution)
├─ 报工与完工      报工记录 /mes/production-reports · 完工入库 /mes/receipts (Data Collection)
├─ 在制与追溯      在制跟踪 /mes/wip · 追溯查询 /mes/traceability          (Tracking)
└─ 生产分析        异常与产能 /mes/capacity                              (Analysis)
★ 移出 MES 顶层菜单（改他域跳链 / 详情内联只读）：质量与不良 → 质量管理；设备与停机 → 设备监控
```
菜单项从 ~16 压到 ~11；每组 1-2 页、语义单一、顺序即生产流；**标签即一线操作**。

### 2.3 合并 / 拆分 / 迁移清单
| 操作 | 对象 | 目标 | 理由 |
|---|---|---|---|
| 迁移 | 规则排程 | 异常组 → 计划与排程 | 属 detailed scheduling |
| 迁移 | 班次交接 | 异常组 → 班中执行 | 执行协同非异常 |
| 拆独立 | 异常与产能 | 异常组 → 生产分析 | analysis 活动 |
| 收 Tab | 派工看板 → 工单页视图 | 同对象不同视图 → 页内 Tab |
| 收 Tab | 生产准备检查 → 齐套页 Tab | 开工 readiness 平级视图 |
| 移出 | 质量与不良 / 设备与停机 | 他域跳链 + MES 详情内联只读 | 他域主对象不占 MES 菜单 |
| 解散 | 「异常与协同」分组 | 五实体各归其位 | 杂物抽屉反模式 |

> **唯一需产品确认**：生产计划 /plans 与规则排程 /schedules 的边界——是「计划数据与排程规则配置」（→ 一页双 Tab）还是两套并行引擎（→ 同组两页）？

## 3. 核心 UX 流修复（执行价值流）

三条核心旅程 + 断点（操作员旅程断点最严重）：

### 3.1 报工就地化（最高优先）
**问题**：工序页「报工」是 `openRoute('/mes/work-orders')` **整页跳工单列表 + query + watch 弹窗** —— 全模块最严重的上下文丢失点；报工弹窗只读工单/工序号，其余纯手填。
**方案**：把报工表单抽成**共享抽屉组件** `ProductionReportDrawer`，由工单行 / 工序行 / 在制行 **就地调起**（删除 query→弹窗 hack）。工序进入锁定该工序；工单进入默认选 Running/Ready 工序（非 `operationTasks[0]`）。

### 3.2 动作接力（消灭死胡同）
派工指派完、急单提交完、报工完工后都缺「下一步」。每个关键动作成功后给**带参后续动作**：
- 派工成功 → 「查看该工序执行」
- 急单返回的受影响工单 → 每个 workOrderId 做成**跳详情链接**（现为纯文本）
- 报工勾「完成当前工序」且**末道工序** → toast 给「去完工入库」带 workOrderId 直达预填

### 3.3 阻塞项可点
派工看板 / 驾驶舱「展示阻塞原因文字但点不动」。阻塞原因应是**带 workOrderId 的跳转**，一键到处理页（齐套/质量/设备），闭合 ISA-95「执行→排除阻塞」环。

### 3.4 角色化落到列表过滤
驾驶舱 roleLanes 已有骨架，但「点进去=全量列表」。给 `operation-tasks` 加**「我的工序」快捷过滤**（`assignedUserId` = 当前登录用户），操作员不再在所有人的工序里翻找。

### 3.5 一线少填（报工自动带出）
照 `dispatch` 派工弹窗的模式：身份/工序/设备/班次**系统带出**，一线只补良品数 / 返修数 / 报废数、已收料批次耗量与是否完成。批次选择只展示当前工序或工单级已收料且仍有可用量的记录；无材料读取权限时不发起批次读取。良品数默认值 = 计划数 − 已报数（剩余应报）。

### 3.6 异常/排程双向链
异常三页（capacity/downtime/quality）与规则排程是孤岛 → 补「源工单回链」（异常行带 workOrderId+operationTaskId）与「工单→排程」正向链。
**统一带参契约**：跨工序操作一律携带 `workOrderId + operationTaskId + workCenterId + skuId`。

### 3.7 领料闭环可视化（跨域：MES 领料申请 → WMS 出库）
**事实（2026-07-31 更正，含尚未落地项的明确标注）**：`MaterialIssueRequestRow` 早就含 `wmsRequestId`（连 WMS 出库）+ `requestedQuantity`/`receivedQuantity`（收料进度）+ `status`，但**字段有 ≠ 闭环有**：本文档 v1 据此写下的「后端闭环已建」是失实的 —— 领料申请创建不发任何领域事件，WMS 从不知道有人领料，`wmsRequestId` 恒 `null`。当前状态请按下面三行读，**不要再把"计划中"当成"已建成"**：

- **已落地（#1324 / PR #1340，已合入 main）**：MES `MaterialIssueRequested` → WMS 建出库单/拣货任务 → `MaterialIssueOutboundPrepared` 回写 MES 的两跳事件链；`wmsRequestId` 至此才真的会被写上值。
- **已落地（#1341 / PR #1355）**：网关 MES 受理回执的显式映射 **14/14 处写面全覆盖**（计划转工单、工单下达/暂停/取消、质量放行强制解除、派工、遥测候选驳回、报缺陷、停机记录/恢复、交接班创建/接班、领料申请、线边收料），修好 `accepted` 恒 `false`、下游单号被丢的缺陷；`downstreamService`/`downstreamDocumentType` 统一用全仓 PascalCase 词表（`BusinessMes` + `WorkOrder`/`MaterialIssueRequest`/…），与集成事件信封的 `sourceService`（kebab，如 `business-mes`）是两张不同的词表，不要混用。
- **仍未落地**：拣货完成 → 线边收料是**人工衔接**（仓库拣完，操作工在 PC/PDA 点「线边收料」），没有自动流转事件，**不算自动闭环**；真正的自动闭环需单独立项（见 PR #1340 的 Followup）。

前端「齐套与物料」页此前不暴露这条链，用户发起领料后看不到后续 → 体验上"断"。
**方案**：领料申请行显式做成「**已收 / 应领进度 + 状态徽章**」，并把 `wmsRequestId` 做成**跳 WMS 出库**的链接（不显 GUID，显「查看出库」）。让「工单缺料 → 发起领料 → WMS 出库 → 收料回写 → 齐套」整条在 MES 侧一眼可见、可追。**领料是开工前的物料门，必须可发现、可追踪。**

### 3.8 齐套口径自解释（#1291）
**问题**：齐套只认「线边可用 + 已备料 + 已收料」，MRP 读的是全厂库存 —— 两个口径都成立，但界面互相矛盾又不解释，
用户看到「原料仓 26,100L 充足」和「缺口 145.86L」同时出现，只会认为系统坏了。
**方案（三件事，缺一不可）**：
1. **显式标注口径**：齐套表格旁常驻一句口径说明，写明核算范围与「MRP 用全厂口径、数字不同属正常」。
2. **缺在哪个环节**：`shortageStage` 由 MES 权威给出 —— `awaitingDelivery`（领料已发起、仓库在配）
   与 `awaitingPreparation`（还没发起领料）两种状态；读面配「下一步动作」文案，不再只甩一个缺口数字。
   聚合「应领」只算**仍然在数**的领料单（`Requested` / `PartiallyReceived` / `Received`）：
   取消、退料中、预留失效的单子不代表仓库还在配货，算进来会让「其实没人在配」被误标成「仓库配送中」。
   「已收」仍对全部单据求和 —— 收到线边的实物是既成事实，取消/退料会自行把 `ReceivedQuantity` 冲回，
   再过滤一次反而会凭空抹掉已消耗量、改动齐套结论。
3. **全厂对照入口**：缺料时给一键穿透到库存可用量页，核对原料仓到底有没有货。
**边界**：齐套仍是**开工硬门**，MES 侧一点不放松；软化的是**排产侧**（见排产工作台文档 §3 物料软约束）。
**已知缺口（跟踪项）**：MES 未持久化用料行的 UOM，齐套读面暂时无法直接内联「全厂可用量」数字做数值对照，
只能给穿透入口；补齐需在 `MaterialRequirement` 上持久化 UOM 并加一条全厂范围的可用量查询。

### 3.9 停机登记入口与失败关闭（#2201）

`/mes/downtime` 在保留既有停机列表和恢复入口的同时，为班组长提供「登记停机」主操作。
登记对象不允许自由手填：页面从当前主体可读的真实工序任务中带出工单、工序、工作中心和设备，
并要求该工序仍被 `business.mes.downtime.manage` 的实时选择范围覆盖；停机原因来自 Maintenance
权威的 `downtime-reason` 可搜索目录，时间由用户按本地时间录入后转换为 UTC 提交。

以下任一前置不成立时必须失败关闭且不发送停机写请求：缺少操作权限、组织或环境、实时写范围、
工序读取范围、工单/工序/工作中心/设备上下文、已配置原因，或时间无效/晚于当前时间。提交前再次
刷新工序和写范围，避免使用已经失效的上下文。服务返回受理结果后展示真实停机事件标识并刷新列表；
服务端拒绝时保留原始原因，同一表单内容的安全重试复用稳定幂等键，只有成功受理或表单意图变化才
结束原意图。既有「确认恢复」入口和恢复协议不因本次登记入口而改变。

本切片不改变导航或 IA，也不新增后端、HTTP/OpenAPI、生成客户端、数据库或其他 MES 写入口。
前端测试覆盖目录的 1-based 分页与服务端页大小上限、原因可用/未配置/读取错误、UTC 与本地时区映射、
成功请求体、服务端原因保留和同键重试；真实 Gateway/RBAC、浏览器端到端及完整运行栈仍需独立联调证据。

### 3.9.1 停机原因读面：原因列、按原因筛选与时长构成（#1947）

登记侧选了原因码之后，`/mes/downtime` 的读面同样按原因组织：表格有「停机原因」列，
工具栏可按原因筛选，页面顶部给一张「停机时长按原因」构成卡，让班组长先看**哪个原因最费时间**，
再点进去看具体事件。

- **原因名由门面解析，页面不自己拼**：MES 只存原因码，中文名在 BusinessGateway 按 Maintenance
  权威的 `downtime-reason` 目录补成 `reasonName` 一并返回（见 API 契约规范第 17 条）。
  目录里没有的码（历史自由文本停机原因）不编名字，读面照实显示原值。
- **统计窗口**：列表与汇总共用按停机开始时刻落窗的半开区间 `[windowStartUtc, windowEndUtc)`；
  两端未传时默认查询时刻之前 30 天。页面提供日期区间控件，默认近 30 天，并与关键字、状态、
  原因筛选并列；切换窗口回到第一页。跨窗停机不切分，已恢复事件计完整时长。
- **汇总口径**：按原因分组给出未恢复事件数与停机分钟数；已恢复事件按恢复时刻结算，
  **未恢复事件累计到查询时刻与窗口右边界中的较早者**，避免查询历史窗口时把至今未恢复的事件
  一直累计到当前时刻。
  名次按时长降序，同时长按原因码升序，保证平局也是稳定名次而不是随机行序。
- **汇总不受原因筛选影响**：汇总在应用 `reasonCode` 过滤之前算完。否则用户选中一个原因后，
  汇总只剩那一行，既看不到别的原因，也没法再换回去。其余筛选（状态、关键字、工作中心、
  班次、设备、统计窗口）与列表同口径。
- **筛选项取自权威原因目录，不取自本次汇总**：汇总只含「当前筛选下真出现过的原因」，
  拿它当下拉选项会让已选中的原因在切状态后从下拉里消失，过滤却仍然生效，用户看不到也取消不掉。

聚合整条下推数据库（按原因 `GROUP BY` + 时长求和），读面不把过滤后的停机行拉回进程：
分页读面每次翻页与每次改筛选都会重算，拉全量等于在最常走的路径上挂一次无界全表扫描。
该聚合的时长差值由 PostgreSQL 计算，SQLite 与 InMemory 都证明不了它，因此由 PostgreSQL lane 用例把关。

**已知缺口（跟踪项）**：世界史种子仍向 MES 停机事实写中文自由文本原因，不在 Maintenance
`downtime-reason` 目录内，因此同一批数据里会同时存在目录码与自由文本两套原因；
读面照实呈现两者，收敛口径见 #2681。

### 3.10 线边库存余额与账龄读面（#1964 / #2229）

Console `/mes/materials` 与 PDA `/mes/issue` 在既有领料流程旁展示同一份 Inventory
权威线边库存读面：物料、站点/线边库、单位、在手、预留、可用、批次数与账龄。
该区域只读，不增加库存写操作，也不由前端拼接 Inventory URL 或复制库存口径。

账龄按仍有余额批次的生产日期计算。全部批次都有生产日期时显示「账龄完整」；只有部分
批次有生产日期时显示可知的最老账龄并明确「部分批次缺少生产日期」；没有可用生产日期时
显示「账龄未知」，绝不把缺失值显示为 0 天。加载、失败、空结果与刷新均是独立状态，失败
不能退化成空库存结论。列表按服务端每页 200 条明确分页，页码参与请求缓存身份；页面同时
展示当前页、总页数、本页条数与总条数，余额超过 200 条时仍可逐页访问且不会静默截断。

### 3.10 工序累计实际工时读面（#2220）

`/mes/operation-tasks` 与 `/mes/production-reports` 使用同一展示口径并列显示实际人工工时和实际机器
工时。该数值是工序完成后冻结的累计实绩；报工列表中的值只是所属工序累计实绩的只读参照，不是本条
报工的人员工时分摊。工序尚未完成或冲销后重新打开时显示「暂无实绩」，服务明确返回零时显示
「0 小时」，两种状态不得互相替代；非整数小时保留有效小数。正非零值小于 0.0001 小时时显示
「小于 0.0001 小时」，不得冒充零值，便于班组长核对短周期作业。

本切片只消费 BusinessGateway 已发布的只读字段，不改变工序/报工写流程、导航、权限、后端契约或 ERP
成本语义。

### 3.11 工单拆分与合并交互（#1963，PR-D）

Business Console 在 `/mes/work-orders/:workOrderId` 提供工单拆分，在 `/mes/work-orders` 提供多选合并。
两项操作都要求当前主体具备工单管理权限和实时授权作业范围；页面只允许对 `Created` / `Released` 工单发起，
不把列表或详情读面当作写权限的替代。拆分必须填写至少两个新的子工单标识，子工单数量均大于零且精确守恒；
合并必须选择至少两个同 SKU、生产版本和单位的源工单，并填写一个新的目标工单标识。列表读面没有单位字段时，
页面不臆造单位，最终单位一致性仍由既有服务端契约判定。

提交前页面展示数量、标识、状态和原因校验；写请求复用稳定幂等键。服务受理后先展示「已受理」，只有按返回的
`transformationId` 成功回读权威变更明细后才显示成功；回读失败保留受理结果并允许重试。服务端拒绝按普通错误或
409 冲突展示，避免把未知结果或过期上下文误报为成功。本切片仅适配已发布的 Gateway 契约，不新增后端 API、
OpenAPI、生成客户端、MES domain 或 persistence；Quality、Inventory、WMS 和 Scheduling 不在范围内。

### 3.12 首件未通过不许批量报工（#1949 波 2 / #2780）

工序的**首件那一件**必须先做出来、报上来、送检，它不被门禁拦；此后同一工单同一工序的报工，
在首件判定合格之前一律被**服务端**拒绝——不是界面禁用，PDA 与 Console 两条报工路径同样受管。

「这一次是不是首件那一件」不由 MES 的报工历史推断，而取质量侧的首件进度：任务尚未开出时这一次
就是首件那一件（开单的唯一触发点就是这次报工），放行；任务已开出未判定、判不合格、判为让步放行，
一律拒。让步放行**不**解锁批量报工——它是对已产出那批件的处置结论，不回答「后面能不能继续批量做」，
纠正后须重新首检合格。首件判不合格后经返工复检合格的，该工序即可继续报工：门禁每次现取最新一次判定，
不缓存首次结论。该物料与工序工作中心没有生效首件检验档时无需首件，报工不受限。

质量侧尚未掌握该工序的工单发布事实时报工被拒，提示稍后重试；质量服务不可用时报工同样被拒——
门禁只有 fail closed 一种姿势，「读不到结论」不等于「合格」。**存量在制工单中，工单发布事实从未
到达质量侧的那一批，会被持续拒绝**：该状态不靠报工恢复，只能靠补上工单发布投影。它由
[#3000](https://github.com/Mang-X/Nerv-IIP/issues/3000)（Quality 工单发布投影回填）一次性解决，
门禁侧不设过渡开关或例外名单。回填由 MES 的内部运维端点
`POST /internal/business-mes/v1/work-order-release-projection-backfill` 触发：它按「工单状态 + 工序未完工」
这一可复算判据选出存量在制工序，把发布事实补投给质量侧；重复执行不改变质量侧投影，也不额外开出首件检验任务。
**部署顺序是硬约束：#3000 的回填必须先于本门禁上线执行**，顺序颠倒会让这批在制工序在回填完成前被持续拒绝。

被拦下时的提示直接点名入口位置；操作员在 `/mes/operation-tasks` 的行操作里就地进入「首件检验记录」。
该入口**只切页签、不带任何单据上下文**——质量检验页一旦在 query 上看到工单/工序/来源单据，就会
自动弹开「创建检验记录」抽屉，把来看结论的人丢进新建表单。首件记录列表按物料与结论过滤，没有工序维度。

本切片不新增首件检验任务的手工建单入口，也不为门禁提供时间开关或例外名单。

## 4. 改造批次与优先级（#420 感知）

价值/频次：越靠「执行+报工采集」越高频、卡住越致命；越靠「分析/配置」越低频。

| 批 | 内容 | 理由 |
|---|---|---|
| **批 1 执行采集主干** | 工序执行 → 报工记录 → 齐套与物料（含 §3.1 共享报工抽屉、§3.4 我的工序、§3.5 少填） | 最高频价值地基，且**不被 #420 卡**，投入产出比最高 |
| **批 2 入口与导航** | §2 IA 导航重构 + 生产驾驶舱（KPI 含义化、§3.2/§3.3 接力与可点阻塞）+ 在制跟踪 | 把执行页串成「角色→任务→报工」动线 |
| **批 3 派工链（壳先行）** | 工单与派工 + 派工看板 | 价值最高但**被 #420 卡内核**（ID→名称、状态 Select）；先做布局/动作/角色泳道，内核挂 #420 不空等 |
| **批 4 班次闭环** | 班次交接 → 生产准备检查 → 完工入库 | 补全「一天的开始与结束」，流程固定风险低 |
| **批 5 排产/分析/他域链** | 规则排程 → 生产计划 → 异常与产能 → 追溯；质量/设备仅做跳独立模块的轻链接 | 低频或有独立模块兜底 |

**MVP（车间能跑）**：工单与派工、派工看板、工序执行、报工记录、齐套与物料、生产驾驶舱（+ 配套 PDA 领料/工序/报工/收货）。

**风险**：派工/工序核心交互（派工 Dialog、可开工判断 `describeMesReadinessReason`）是生产关键路径，**只补 IA/层级/空态/接力，不重写核心逻辑**——避免为改而改、改坏停产。

## 5. 复用基础数据经验（playbook 落地到 MES）
- **FE-2 区块拼装**、不裸表、不改 shadcn 原版（同主数据 §0）。
- **SectionCards 非默认**：MES 驾驶舱/各页**禁机械计数 KPI**（`本页X` / 裸 `reduce` 计数）→ 改**含义化语义**（待开工 / 超期 / 阻塞待排除，能驱动动作）。
- **说人话**：UI 不暴露 GUID/工程语言。MES 的 ID→名称受 **#420** 卡 → facade 就绪前**标注**，不硬显 GUID 当标识。
- **IA 判定规则**（模板第 6 节）：父子→树；同对象视图→页内 Tab(≤5、不进菜单)；弱关系→拆独立页；主+受控子集→主从。MES 按此判（§2.3）。
- **提交时校验、toast 反馈、诚实数据、空态给出路**（同主数据 §5/§7.2）。
- **§1.5 两轮自检**（实现前 A + 完成后 B）每页过。
- **视觉验证不跳过**：每页改完用 Claude-in-Chrome 截真实运行页核对（本轮已打通）。
