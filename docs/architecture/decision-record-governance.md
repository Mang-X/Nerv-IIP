# 决策记录内容分层治理

## 目的与权威来源

本文件规定一段内容该住进 `docs/adr/` 还是 `docs/architecture/`，以及决策记录里
**不得**出现哪些内容。`docs/AGENTS.md` 是触发入口，本文件是分层判据与完成条件的
权威来源。结构不变量由 `scripts/verify-adr-format.ps1` 强制；本文件登记的欠账在
补齐之前不进门禁，避免文档强度高于实现强度。

产品文档站不在本文件范围内：它是 `frontend/apps/docs/docs/` 下的 VitePress 应用，
四象限落点由 `docs/adr/0021-product-docs-information-architecture.md` 治理。

## 唯一判据：这段内容什么时候会变

分层不按"是不是决策"，按**变更频率**。把不同变更频率的内容放进同一个文件，是
`docs/adr/` 与 `docs/architecture/` 当前混杂的根因。

| 内容 | 什么时候会变 | 落点 |
| --- | --- | --- |
| 决策、理由、被否决的备选、复评触发条件 | 只被新决策取代，**永不就地编辑** | `docs/adr/`（架构类）或 `docs/architecture/` 的决策记录（流程/CI/测试类） |
| 实施状态、责任票映射、进度声明、"截至某日尚未实现" | 每次实施推进都变 | GitHub / Linear 票面 + `docs/architecture/implementation-readiness.md`，**不进决策记录** |
| 参考数据表（旧名→新名映射、token 全表、字段字典） | 随代码增长 | `docs/architecture/` 的参考页，或代码旁生成物 |
| **描述性**技术规格：记录实现当前如何做（当前状态流转、现有时序、已实现的错误处理） | 随实现变 | `docs/architecture/` 的规格文档，或代码旁契约 |

判断一段内容是否该留在决策记录里，只问一句：**下一次实施推进会不会让这段话变成
过期描述？** 会，就不属于决策记录。

### 表达形式不决定归属

**规范性的图与表仍然是决策。** 状态机、时序图、失败矩阵、接口清单这些形式既可以承载
「实现当前这样做」（描述性，随实现过期），也可以承载「实现必须这样做」（规范性，实现
必须向它收敛）。判归属看语气而不看形式：

- 表头是 `必须结果 / 禁止结果`、散文里是 `不得 / 只能 / 必须`、且不含实现类型名与代码
  路径 → 规范性，属决策，留在 ADR。
- 陈述某个类当前如何实现、带日期或"当前/尚未"字样、引用具体实现标识符 → 描述性，
  移交规格文档或代码旁契约。

这条不是抽象原则：一次审计曾按小节名（含「矩阵/状态机/时序/接口」）把 ADR 0023
的 `## Upload session 状态机`、`## Complete 提交时序`、`## 失败矩阵` 与 ADR 0024 的
`## 健康与失败矩阵`、`## 后续层接口` 全部登记为待搬迁，逐节读全文后发现五节都是规范性
裁决——零现状陈述、零日期、零实现标识符，且 ADR 0023 的状态机与时序正是该篇标题承诺的
「complete 提交不变量」本身，搬走会抽掉这篇的实质。**按小节名分类会误判，必须逐节读全文
并套用上面的语气判据。**

## ADR 的职责与规范骨架

`docs/adr/` 只收**架构决策**：服务边界、契约、存储与消息基线、命名空间与样式隔离、
部署拓扑这类关于"我们交付的系统长什么样"的裁决。

规范骨架（`##` 级小节，按此顺序）：

```markdown
# ADR NNNN：<标题>

- 状态：已接受 | 已否决 | 被取代 — <一句话说明>
- 日期：YYYY-MM-DD

## 背景
## 决策
## 理由
## 实施说明
## 已考虑的替代方案
## 后果
## 范围之外
```

- `## 背景` 与 `## 决策` 必写。`## 决策` 允许拆成 `## 决策 1：…`、`## 决策 2：…`。
- 领域专属的技术小节（拓扑、契约、清单）可以自由出现在必写小节之间。
- `## 范围与非范围` 是合法的**另一个**小节，不是 `## 范围之外` 的同义写法：前者
  同时界定范围内与范围外，后者只列不在范围内的事项。按内容选，不要互换。

### 同义异名禁用表

同一语义三套写法会让门禁无法校验，也让读者以为它们指不同的东西。左列一律不允许：

| 禁用 | 规范值 |
| --- | --- |
| 影响、结果 | 后果 |
| 范围外事项、范围外 | 范围之外 |
| 备选方案、替代方案、已考虑的方案 | 已考虑的替代方案 |

### 生命周期禁用标题表

决策记录写的是裁决，不是进度。提案期（还没定）与进度期（做到哪了）的段落一旦落进 ADR，
读者就得读完全文再自行推断哪一条还有效；「日期戳增量段落」「实施状态与票映射」两档欠账
（见下文欠账表）正是这么长出来的。下表左列的标题一律不允许出现在 `docs/adr/` 的任何
`##` 及以下级别标题上，由 `scripts/verify-adr-format.ps1` 强制：

| 禁用标题 | 匹配方式 |
| --- | --- |
| `实施` | 前缀 |
| `迁移计划` | 前缀 |
| `验收标准` | 前缀 |
| `验收条件` | 前缀 |
| `当前实现` | 前缀 |
| `下一步` | 前缀 |
| `待办` | 前缀 |
| `计划` | 前缀 |
| `路线图` | 前缀 |
| `进度` | 前缀 |
| `票映射` | 前缀 |
| `Proposal` | 全等 |
| `Plan` | 全等 |
| `Migration plan` | 全等 |
| `Acceptance criteria` | 全等 |
| `Next steps` | 全等 |
| `TODO` | 全等 |
| `Roadmap` | 全等 |
| `Implementation status` | 全等 |

禁令对状态值域里的三种状态一视同仁：`已接受` 的记录不该留提案期段落，`被取代` 的记录保持当时
事实、同样不该有进度叙述，`已否决` 亦然（`已否决` 的骨架校验是另一件事，属被否决决策落盘那张票，
这里不扩展）。

匹配方式的选择有理由：中文项按前缀匹配，因为同一档欠账有多种写法（`实施状态` 与
`实施状态声明`、`当前实现事实` 与 `当前实现事实与目标状态`），全等表每来一个变体就要补一行；
英文项按全等匹配，因为英文词在中文标题里做前缀会误伤合法的领域小节（例如
`## Complete 提交时序`）。全等匹配忽略大小写，其余比较一律序数。

**白名单：`## 实施说明`**。它是本仓库既定约定，部分取代的编号项就住在
这里（见下文「部分取代」）。它必须先于 `实施` 前缀判定，否则前缀禁令会把它连带禁掉。
白名单只豁免上表的标题禁令，不豁免日期戳禁令。

**日期戳标题**：任何 `##` 及以下标题只要含 `YYYY-MM-DD` 形式的日期就是违规——决策变了要新开
记录，不要在旧记录上按时间叠加段落（见下文「决策变更不叠段落」）。

**门禁只查标题，不查正文。** `## 实施说明` 正文里的票号与日期（例如「#206 是 APS lite 的
执行入口」「2026-07-03 起，第 8 条不再成立」）是耐久指针和部分取代的规定写法，不是进度叙述；
下探正文会误伤，因此明确不做。

上表与 `scripts/verify-adr-format.ps1` 里的 `$lifecycleForbiddenPrefixes`、
`$lifecycleForbiddenExactHeadings`、`$lifecycleSectionAllowlist` 三个列表逐字对齐，由
`scripts/tests/verify-adr-format-lifecycle.Tests.ps1` 双向锁定：文档加一行门禁不查、或门禁加
一条文档没写，该测试都会红。

## 决策变更不叠段落，用新记录取代

决策变了，**不要在旧 ADR 上追加带日期戳的补遗段落**。那会把决策记录变成变更日志：
读者必须读完全文再自行推断哪一条还有效。

正确做法是新开一条记录并建立双向链接。整篇取代与部分取代的做法不同，按实际情形选。

### 整篇取代

旧记录的状态改为 `被取代 — 由 ADR NNNN 取代`，新记录在 `## 背景` 里说明它取代了什么、
为什么。旧记录的原始判断保持原样，作为当时事实。

### 部分取代（只有若干条款被推翻）

旧记录其余条款仍然有效，因此**状态保持 `已接受`**，不得整篇标为被取代。仓库已有一套跑通的
做法，照它办：ADR 0012 被 ADR 0014 部分取代时，四件事同时成立——

1. **旧记录头部加一行** `- 修订依据：[ADR NNNN：<标题>](NNNN-slug.md)`，让读者在头部就知道
   本篇有修订。
2. **旧记录的 `## 实施说明` 追加一条编号项**，写明「YYYY-MM-DD 起，第 N 条与后果第 M 条的
   某表述不再成立；ADR NNNN 把它改为……；仍然后置的部分是……」。放在实施说明而不是新起段落，
   是为了不让文件出现按时间叠加的小节。
3. **原条款文本一字不动**，保留为当时事实——不要就地改写历史判断。
4. **新记录的 `## 背景`** 精确点名被推翻的条款号，`## 已考虑的替代方案` 至少登记「维持旧记录
   原判断」这一个被否决方案。

ADR 0014 ← ADR 0025 是第二个按此办理的实例（决策第 8、10、23 条与后果第 6 条被部分取代）。

## `docs/architecture/` 的两种角色

该目录同时承载两类文档，写作要求不同：

- **权威规则文档**：陈述当前必须遵守的规则（如 `document-language-governance.md`、
  `script-automation-governance.md`）。只写现态，不写历史。
- **决策记录**：流程、CI、工具链、测试策略的裁决。范本是
  `backend-ci-build-strategy.md`——它逐条列出备选方案并带裁决词（「排除」/「不采用」）、
  附实测数据、还给出**复评触发条件**。新增此类文档照它的形状写。

`implementation-readiness.md` 是**状态台账**，属于上表第二行：它记录阶段与进度，
不承载裁决。裁决应住在对应的权威文档或决策记录里，由台账引用。

## 门禁强制什么

`scripts/verify-adr-format.ps1`（在 CI 的 Script Governance job 中运行）逐篇校验：
文件名 `NNNN-kebab-case.md`；首行 `# ADR NNNN：<标题>`（全角冒号）；**H1 编号与文件名编号
一致**；**编号全局唯一**；`- 状态：` 值在允许集合内；`- 日期：YYYY-MM-DD`；`## 背景`、
`## 决策` 与 **`## 已考虑的替代方案`** 存在；同义异名小节不出现。

自 #1887 起还校验**生命周期禁用标题**：上文「生命周期禁用标题表」的前缀项与全等项都不得出现
在任何 `##` 及以下标题上（`## 实施说明` 是唯一白名单），且任何该级别标题都不得带 `YYYY-MM-DD`
日期戳。门禁只看标题，不看正文。该禁令守的不是存量，而是让已清理的两类内容不再长回来；鉴别力由
`scripts/tests/verify-adr-format-lifecycle.Tests.ps1` 的变异矩阵证明（逐条禁用标题各插一次必红、
`## 实施说明` 不红、日期戳标题必红、文档表与脚本列表不一致必红）。

## 审计口径

按本文件的判据审计 ADR 时，逐篇核这六类内容是否混入决策记录：缺 `## 已考虑的替代方案`、
日期戳增量段落、实施状态与票映射、可搬迁的技术规格与矩阵、参考数据附录、编号撞号。

前两类已由 `verify-adr-format.ps1` 门禁强制，其余四类靠人工判定。判别口径见上文「唯一判据」
与「表达形式不决定归属」——**规范性裁决不因写成矩阵或状态机就变成可搬迁的规格**；备选只回收
不发明，原文没写落选理由就如实写「原文只记录了该选择」。

清理时每批都须核入链：搬走或改名的记录，全仓引用要同批改完。
