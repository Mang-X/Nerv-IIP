# Test Evidence Governance

MAN-661 provides the repository-owned evidence path for backend and Connector Host VSTest runs. The owner is **Nerv-IIP Platform CI/Test Governance**. This document is the operator contract; the approved architecture remains in the MAN-661 design.

## Runtime and retained artifacts

CI runs `dotnet test` normally with `--logger trx`. Test steps have no `continue-on-error`, shell pipeline, or status-restoration wrapper, so their natural exit code remains authoritative. Collection and upload use `if: always()` so failed runs still publish diagnostics when normalized evidence exists.

Since MAN-669 the backend fast gate runs as four shard jobs instead of one. Each shard job runs `scripts/run-backend-test-shard.ps1`, which emits `trx;LogFilePrefix=<job id>` into its own job-local raw directory, and each job then invokes the same single-lane collector for the one lane it owns:

| Lane | CI job | Shard |
| --- | --- | --- |
| `backend-shard-1` | `Backend Tests - BusinessGateway` | `business-gateway` |
| `backend-shard-2` | `Backend Tests - Platform` | `platform` |
| `backend-shard-3` | `Backend Tests - Business Core A` | `business-core-a` |
| `backend-shard-4` | `Backend Tests - Business Core B` | `business-core-b` |
| `connector-host` | `Connector Host Tests` | — |

`Backend Tests` remains the stable required aggregate. It runs no tests, owns no evidence lane, and only asserts that shard governance and all four shard jobs succeeded. `scripts/verify-backend-test-shards.ps1` enforces this wiring structurally: the lane/job binding, the raw-only results directory, the exact collector arguments, and exactly one redacted evidence artifact per shard job. A shard job that uploaded its raw directory, claimed a sibling lane, piped the runner through a shell, or downgraded collection to `success()` fails that gate.

A shard that fails or times out prints its buffered stdout/stderr to the Actions job log **after redaction**; those buffers are never written to an uploaded file.

`run-backend-test-shard.ps1` excludes real-dependency selectors with `FullyQualifiedName!~`, so those tests are absent from shard TRX rather than present as registered skips. Two gates keep that exclusion honest instead of turning it into a private escape hatch:

- **Policy closure and owner-lane derivation.** Every fast-shard exclusion selector must resolve to at least one policy test identity whose rule is `environment-gated` with a real-dependency `requiredLane`. A test cannot be dropped from the default gate unless this document's skip policy already registers it. The shard's declared `excludedTestLanes` must then equal the heavy lanes those `requiredLane` values map to (via `heavyLanes[].policyLane`), so a shard cannot attribute a `full-chain` exclusion to the real-PostgreSQL owner script. All 49 current selectors resolve to `postgres` or `full-chain`; enforcement lives in `verify-backend-test-shards.ps1`. Passed-execution proof stays with the opt-in `scripts/verify-backend-real-postgres-tests.ps1`, which is a registration-level separation only — the heavy lanes are not wired into CI yet.
- **Selector anchoring.** VSTest `!~` is a substring match, so a class selector is emitted with a trailing dot (`FullyQualifiedName!~Ns.XTests.`) and cannot swallow a sibling class that merely shares its prefix. Method selectors stay unanchored so parameterized cases keep matching; governance compensates by scanning the registered MAN-661 source file and rejecting any method selector whose name is a prefix of another member in that file.
- **Per-project execution.** After a shard runs, every project it classifies must appear in the shard's own TRX with at least one executed result, and the shard must not execute an assembly it does not classify. This reads the same `UnitTest/@storage` attribute the collector uses. It deliberately does **not** scan dotnet console text: that text is localized, so a phrase match fails open on any non-English runner — the exact silent pass this boundary exists to prevent.

Raw files live only at `artifacts/test-evidence-raw/<run>/attempt-<n>/<lane>/` during the job. The raw TRX, stdout, stderr, attachments, collector payloads, request/response bodies, and arbitrary result files are never uploaded. Retained artifacts are redacted and written to:

```text
artifacts/test-evidence/<run>/attempt-<n>/<lane>/
├── trx/                 # reconstructed, normalized TRX only
├── tests.jsonl          # one schema-v1 record per runtime test
├── summary.json
├── summary.md
└── diagnostics.log
```

Credential URL user info, bearer authorization, quoted or unquoted password/token/secret/client_secret values, PEM blocks, and named `customerName`, `phone`, `email`, and `address` fields are replaced before retention. Parameterized display-name values named `body`, `requestBody`, or `responseBody` are matched case-insensitively and replaced with a non-reversible 16-hex digest marker; nested/escaped values and multiple body parameters are bounded structurally, while method identity and non-body parameters remain available for skip-policy matching and instance distinction. Raw failed-test messages and unregistered skip reasons are omitted by construction; approved skip reasons are bounded to 512 characters. A collector failure publishes a retained bundle with `collectionStatus: failed`, an `evidence-collection-failed` summary, allowlisted and bounded run identity/diagnostics, and a nonzero exit. If the requested output directory already contains files, the failure bundle uses the first free deterministic sibling (`.failure`, `.failure-2`, ...) and reports that exact path through the collector step output; upload consumes that output and never overwrites the pre-existing directory. Retention is 14 days. GitHub permissions are only `actions: read` and `contents: read`.

## CI timeout budgets

Evidence collection is only reachable if the job survives long enough to reach it. A job-level `timeout-minutes` cancels the **whole** job, `if: always()` steps included, so a job that hits its own budget publishes no evidence at all — the MAN-799 `Connector Host Tests` hang burned 28 minutes and produced nothing.

Two rules apply to every job in `.github/workflows/ci.yml`, and a third applies only where evidence exists:

1. **Every job declares `timeout-minutes`.** A job without one inherits GitHub's 360-minute default and can burn a full runner hour-block on a deadlock.
2. **Every explicit step declares `timeout-minutes`** — checkout, SDK/pnpm setup, cache restore, and the evidence collection/upload steps included. `if: always()` does not exempt a step from having a budget.
3. **A job that publishes evidence keeps the sum of its step budgets strictly below its job budget.** This is what makes its job budget unreachable in practice: some step must exceed its own budget first, and a step timeout fails only that step, so the job continues into `Collect …` / `Upload …` and the redacted bundle is still published. A single unbudgeted step reopens the path where the job budget fires first and takes the artifacts with it.

Rule 3 is deliberately scoped. The four backend fast shards (`backend-tests-business-gateway`, `backend-tests-platform`, `backend-tests-business-core-a`, `backend-tests-business-core-b`), `erp-sales-order-demand-acceptance`, and `connector-host-tests` have `if: always()` collection/upload steps and therefore something to lose, so their job budgets are inflated well past any real runtime to clear the step sum. `backend-tests` (the test-free aggregate that MAN-669 left behind), `backend-test-shard-governance`, `frontend`, `openapi-client-drift`, and `script-governance` have no step that can run after an earlier one failed: nothing is preserved by outliving their own budget, so inflating them past the step sum would only convert a fast red into a slow red.

In tier B the **job** budget is therefore the fail-fast bound, sized from observed runtime, and the step budgets are per-step upper bounds only. They are deliberately *not* claimed to be individually reachable: `frontend` sums 58m of step budget inside a 20m job, so its 15m build budget can never fire on its own — the job budget always arrives first. The single tier-B rule enforced by the gate is the case that is dead under every schedule: a step budget at or above the whole job budget. Step budgets are kept in both tiers, in tier B as documentation of what a healthy step costs and as the bound that does fire when a job has only one long step.

### How a job's tier is decided

The gate reads each step's `if:` and asks one question: can this step still run after an earlier step in the same job failed or timed out? `always()`, `!cancelled()` and `failure()` all answer yes, in any legal spelling — `${{ always() }}`, `always() && github.event_name == 'push'`, a trailing `# comment`. Per GitHub's own rule an `if:` expression containing none of the status-check functions is evaluated as `success() && (expression)` and answers no.

Classification fails **closed**: anything the reader cannot decide from the step itself — an `if:` continued on later lines as a block scalar, a YAML alias, an unrecognized function call — is treated as tier A, the stricter tier. The first version of this gate matched only the literal string `always()`, which quietly demoted a job to tier B for every other spelling and switched off rule 3 entirely; the current classification is covered by a fixture per spelling, including negative controls that must *not* promote.

### What the step budgets are, and what the margin covers

Step budgets are generous round upper bounds rather than a uniform multiple of anything: long steps (`dotnet test`, `pnpm build`, the verify scripts) are roughly 2x their observed maximum over the recent run history, while short fixed-cost steps such as checkout, `setup-dotnet`/`setup-node`/`pnpm/action-setup`, and cache restore get a 3–8 minute floor no healthy run comes near. Reading "~2x observed" onto a 10-second checkout would be wrong.

A budget is only a fail-fast bound while the observation behind it is still true. When a change makes a step materially faster, its budget is re-derived from the new measurement rather than inherited — otherwise the job keeps a bound sized for a runtime that no longer exists, which is indistinguishable from having no bound. MAN-663 is the worked example: it took the BusinessGateway shard's test step from 14.7m to 1.0m, so that step moved from the "~2x observed" rule to the fixed-cost floor (35m → 8m) and its job budget from 70m to 43m. Note what the tier-A invariant does *not* let you do: the job budget can never drop below the sum of the mandatory step budgets, so that job budget is a structural floor, not a runtime claim — the budget that actually fires on a hung shard is the test-step budget. (MAN-669 PR-A then re-derived both again for the rebalanced topology; the current numbers are the 10m step / 39m sum / 45m job in the next paragraph.)

The same rule applied a second time when MAN-669 PR-A rebalanced the shard contents. The old per-shard spread (BusinessGateway 8m, Platform 10m, Business Core A 15m, Business Core B 12m) was derived from a topology in which one shard carried 357s of TRX elapsed and another 23s. Re-homing projects by measured cost removed that spread. Across three runs of the branch (`31114441118`, `31115903098`, `31116998822`) the shards measured test steps of 3.5m / 3.0m / 4.2m / 2.4m, then 4.5m / 3.0m / 4.2m / 3.3m, then 4.7m / 3.1m / — / 3.1m. Hosted-runner variance on the *same commit* is tens of percent and moves which shard tops the list, which is itself the argument for one shared budget rather than four: per-shard budgets would encode noise. All four now take a 10m test-step budget (~2x the 4.7m maximum across the three runs), a 39m step sum and a 45m job budget. A budget inherited across a topology change is the same failure mode as a budget inherited across a speed-up: it describes something that no longer exists.

Rule 2 covers the **explicit** steps in `steps:` — the only ones that can carry `timeout-minutes` at all. GitHub also runs steps that are not in `steps:` and cannot be budgeted: `Set up job` before the first step, and the implicit post steps of composite actions (`actions/cache`'s post-save, `setup-node`'s post-cache). The job budget starts before `Set up job` and keeps running through the post steps, so a job's remaining margin — job budget minus step sum — has to absorb them. Current margins are 6m on each of the four backend fast shards, 9m (`erp-sales-order-demand-acceptance`) and 9m (`connector-host-tests`) against implicit overhead observed in the tens of seconds.

The evidence conclusion survives this gap: implicit post steps are scheduled **after** the last explicit step, so they run after `Upload … test evidence` has already published the artifact. They can consume job budget; they cannot cost evidence. What they can do is push a job into its job budget even though every step stayed inside its own — which is why the margin, not just the strict inequality, is part of the design.

### Enforcement

This is not a comment-only convention. `scripts/lib/CiWorkflowBudgets.ps1` reads the workflow structurally and `scripts/tests/test-evidence.Tests.ps1` fails on `missing-job-timeout`, `missing-step-timeout`, `evidence-job-budget-not-above-step-sum`, or `job-budget-not-above-largest-step`; the Script Governance CI job runs that suite directly, so a violation propagates a real nonzero exit. The reader cross-checks its parsed step count against the raw file and throws on a mismatch, so a workflow it cannot parse fails closed instead of reporting zero violations; a job header it cannot read throws for the same reason, because skipping it would merge that job's steps and budget into the previous job. The cross-check resolves each six-space sequence item against its own enclosing job-level key rather than trusting indentation alone — `needs:` and `strategy.matrix` items sit at exactly the same column as step entries, and counting them as steps turned every workflow that uses them into a hard red naming a parse error instead of the real finding. The same suite carries negative fixtures for each violation code and for each `if:` spelling, so "zero violations on `ci.yml`" is a result and not a vacuous pass.

Consequences for anyone editing the workflow: adding or reordering a step in a tier-A job means adding its budget **and** raising the job budget to keep the sum strictly below it; adding any step to a tier-B job whose `if:` can run after a failure — in any spelling — promotes that job to tier A, and its budget has to be raised accordingly.

## Schema v1

| Area | Required fields |
| --- | --- |
| Test record | `schemaVersion`, `workflowRunId`, `runAttempt`, explicit `headSha` and `testedSha`, lane/project/assembly, method identity, bounded parameterized `displayName`, stable `definitionId`/`testInstanceId`, exact `durationTicks` plus derived `durationMilliseconds`, outcome, approved `skipReason`, redaction count |
| Outcome | `passed`, `failed`, or `skipped` |
| Summary | run/job/runner/artifact name, retention days, and retention location; `selectedLanes` plus `selectedLaneResults`; passed/failed/skipped/executed/total per logical selected lane and lane+assembly; summed test duration; separate TRX elapsed duration; slowest tests/assemblies; skip aggregation; concrete baseline source and compatible report-only delta or structured `unavailableReason`; redaction count; attempt classification; violations |
| Lane | `<family>` or `<family>-shard-<positive-integer>` |

`headSha` is the branch head reported by the GitHub event. `testedSha` is the commit actually checked out and tested (`git rev-parse HEAD`). On `pull_request`, `testedSha` may be GitHub's synthetic merge commit and therefore differ from `headSha`; on the supported non-PR `push` event they must be identical. Both EvidenceRoot refresh and the legacy GitHub-console import derive `testedSha` from the independently downloaded job log instead of copying the run head or trusting an artifact to certify itself. Current workflows log `tested-sha=<sha>` after checkout; historical-console compatibility accepts only the exact checkout `git log -1 --format=%H` command and its following SHA. A missing or conflicting checkout authority fails closed. PR checkout provenance may retain distinct branch-head and synthetic-merge SHAs, but a PR run is not eligible to generate the committed baseline. Normalized TRX root attributes carry both values and must match parser run metadata.

`testInstanceId` prefers the persisted TRX `executionId`; only source TRX without a valid execution ID uses the deterministic fallback. `durationTicks` is the reversible 100 ns representation used to reconstruct normalized TRX, avoiding floating-point millisecond drift. `backend-shard-1` is therefore an ordinary schema-v1 lane. MAN-669 added shard lane invocations only: no shard envelope, no second collector, and no change to the record or summary schema.

Normalized TRX is a deterministic retained interchange format, not the original runner timeline. Its `Times` element uses the fixed synthetic start `2000-01-01T00:00:00Z` and derives finish only from retained TRX elapsed duration; consumers must not interpret those timestamps as wall-clock execution time. Raw TRX remains job-local and is never uploaded.

## Skip policy

`scripts/test-evidence-policy.json` has `{ schemaVersion, lanes[], sources[], rules[] }`. A source row identifies one repository-relative C# `Skip =` assignment by path, one-based ordinal, and anchored source-reason pattern. A rule identifies the source, classification, anchored runtime test/reason patterns, an exact `testIdentities` set with `expectedRuntimeTestCount`, allowed lanes/OS, optional required lane, and quarantine metadata. Source/rule references are closed in both directions, so a new method using a shared Fact attribute cannot silently consume an existing class-wide budget.

Every runtime skip must match exactly one context-applicable rule. The current inventory is 40 source assignments:

- `optional`: a capability was not selected; selecting its capability lane makes that skip illegal.
- `environment-gated`: a real dependency was not selected; selecting `requiredLane` requires execution.
- `quarantined`: temporary only, with responsibility issue, ISO expiry date, and measurable exit condition.

Each source assignment is registered by repository-relative file plus one-based `Skip =` ordinal and anchored reason. This deliberately prevents a shared Fact attribute from silently expanding a runtime budget, but it has an explicit maintenance cost: inserting an earlier `Skip =` in the same file shifts later ordinals, so the author must review and update every affected source row.

There are exactly three semantic hard gates:

- `unregistered-skip`: missing, multiple, reason-mismatched, or contextually illegal skip match.
- `illegal-quarantine`: missing/invalid metadata or expired quarantine.
- `zero-execution`: a selected `realDependency: true` lane has no passed or failed runtime result; skipped is not execution.

The collector is a single-lane collector: one invocation owns one physical `-Lane`. `-SelectedLanes` may name that physical shard or its logical base lane; sibling shard selectors must not be used to claim that the invocation certified each sibling. Zero-execution groups multiple selected sibling selectors by logical base only to avoid duplicate/false sibling failures, recognizes a base selector's current-shard execution, and still fails when the selected current shard truly has no passed/failed result. MAN-669 added lane names and invocations but did not change this collector contract. Current CI wires `backend-shard-1` … `backend-shard-4` and `connector-host`, all `realDependency: false`; PostgreSQL, FullChain, performance, and connector real-dependency job wiring remains follow-up work. The CI-wired contract suite proves the zero-execution function, but that is not evidence that a real-dependency job has run.

Timing, trends, skip totals, baseline deltas, and `recovered-after-rerun` are report-only. A recovery label requires an authenticated GitHub Actions lookup of the exact prior attempt and the lane's allowlisted job name, matching workflow run, current attempt, and branch-head SHA, with a failed prior job plus a successful current native test step with nonzero execution, zero failed tests, and zero policy violations. `Get-NervTestEvidenceLaneJobs` is the single allowlist behind both the recovery label and baseline authority. It has exactly five entries — the four backend shard lanes and `connector-host` — and each is bound to exactly one job name, so a shard can never certify a sibling. The unsharded `backend` lane is deliberately **absent**: since MAN-669 no job produces it, and leaving it mapped to `Backend Tests` would have let the test-free aggregate certify a lane it never ran. `backend` remains a valid logical base lane for `-SelectedLanes` and for the policy's `allowedLanes`; it is simply no longer certifiable. Rerun classification is therefore per shard: one shard recovering after a rerun does not relabel the others. The production collector exposes no caller-supplied or test-only authority replacement parameter; tests call the pure response validator directly. When lookup is unavailable the summary says `prior-attempt-unavailable`; attempt number alone never proves recovery.

## Timing data is a cache, not a governed asset

MAN-661 originally kept two different kinds of thing in one governed file: a **policy** list — which skips are registered, which quarantines are legal, which determinism debts are owed — and a **measurement**, how long each assembly took. Only the first is an asset. A policy is written down by a person and a gate holds them to it; a measurement is observed, and nobody decides how fast a test suite is.

Governing the measurement is what produced the failure #1507 removes. The committed snapshot keyed timing rows on `lane + assembly`, so a change with no test content at all invalidated keys: MAN-663 changed the shared BusinessGateway host, MAN-669 PR-A re-homed 17 of the 64 backend assemblies between shards, and both times a human had to regenerate and re-commit the snapshot to clear the resulting `lane-assembly-not-in-baseline` rows. That ceremony was the bug, not the drift.

Every mature implementation treats timings as a cache: CircleCI `--split-by=timings`, Jest `--shard`, pytest-split and Knapsack all read the last successful run's artifact, and a stale or missing entry only makes the split slightly uneven. None of them hashes the timing file, gives it a refresh trigger, or gates on it. Conversely the lists that genuinely are governed — Chromium test expectations, Kubernetes flaky-test quarantine — key on test name or path, never on runner topology, so a re-shard cannot lose a key.

The boundary in this repository is therefore:

| | Timing (measurement) | Policy (governed list) |
| --- | --- | --- |
| Key | assembly | test full name / source path + ordinal |
| Storage | `artifacts/backend-test-shard-timings.json`, gitignored, never committed | `scripts/test-evidence-policy.json`, `backend/test-determinism-baseline.json` |
| Source | aggregated automatically from recent successful `main` runs | written by a person, reviewed |
| Refresh | automatic, on read, no human step | a deliberate edit in the same PR as the change |
| Missing entry | report-only warning plus a fallback estimate | hard gate |

Concretely:

- `scripts/update-backend-test-shard-timings.ps1` aggregates the last **five** successful `main` push CI runs' retained TRX evidence artifacts into the cache. Five, because hosted-runner variance on the *same* commit is tens of percent and moves which shard tops the list, so one run is a sample rather than a measurement; five samples let the **median** absorb a noisy neighbour or a mid-rollout runner image without outlier rules, and at this repository's `main` push rate five runs sits well inside the 14-day artifact retention. An assembly observed twice in one run (two lanes) is summed first, so it counts as one sample rather than two half-samples. Both numbers are defaults, argued in `scripts/lib/BackendTestShardTimings.ps1`, and `-RunCount` overrides the window.
- `scripts/report-backend-test-shard-balance.ps1` prints per-shard totals and the spread. It refreshes a cache older than 24 hours by itself, so there is no human refresh step. **It cannot fail on timing data.** An assembly with no observation is balanced with an estimate — the median of its own shard's measured assemblies, or of every measured assembly when the shard has none, or a fixed last-resort value when nothing has been measured — and reported as a `timing-assembly-missing` warning. A completely unavailable source reports `timing-source-unavailable`. Both exit 0. The only nonzero exit is a structurally unusable manifest, which is a defect in a governed file.
- Degradation is the normal path, not an error path. No GitHub CLI, no token, an offline runner, expired artifacts: each produces a warning, falls back to the last committed evidence snapshot, and then to estimates. This is why the balance report is deliberately **not** wired into CI as a gate.
- The comparison key inside `New-NervTestEvidenceSummary` is now the **assembly alone**. Lane survives on the row as provenance and is used only to disambiguate an assembly the snapshot records under two lanes; a row for neither lane reports `ambiguous-assembly-in-baseline` rather than picking one. An assembly the snapshot never recorded reports `assembly-not-in-baseline`, and a summary with no comparable row reports `no-compatible-assembly`. All of them stay report-only.
- The three semantic hard gates are untouched by all of this: `unregistered-skip`, `illegal-quarantine` and `zero-execution` still fail closed, and they key on test identity, source path and logical lane — dimensions a shard rearrangement cannot move. `scripts/verify-backend-test-shards.ps1` remains the policy gate over the shard manifest and reads no timing data at all; that boundary is asserted in `scripts/tests/backend-test-shards.Tests.ps1` as an AST judgement (no dot-source of the timing library, no call to a function it defines, no timing file named in an evaluated string) rather than as a scan of the raw source, because a comment that merely mentions a timing file is not a dependency. The judgement covers the gate **and every `scripts/lib` library the gate dot-sources**, derived from its own dot-source statements rather than listed, since a timing call moved one hop into a shared library is the same dependency and the entry point’s AST cannot see it. The same suite carries a simulated shard rearrangement, and it is deliberately a *strong* one: it moves a project together with its exclusion selectors and the `excludedTestLanes` those selectors derive, so it reaches the one rule where a shard id meets a MAN-661 lane, and it then feeds the rearranged manifest to the real policy gate as a process and requires it to pass. Policy keys are derived by the production helpers (`Get-BackendTestShardPolicyIdentityMatches` / `Get-BackendTestShardPolicyIdentityKey`) rather than re-derived in the test, and three controls keep the result from being free: the same derivation with the lane spliced back into the key demonstrably loses keys on this rearrangement, the old lane-keyed timing lookup demonstrably loses several, and the same rearrangement with `excludedTestLanes` left behind is rejected at exactly that coupling point.

Comparing key *sets* across a rearrangement is necessary and not sufficient, because most ways of breaking a key are rearrangement-invariant too — a key that dropped the test identity and degenerated to `source|rule` compares equal on both sides, and so does one that returned a constant. Three further contracts in the same suite close that: the key is split back into its segments and each compared against the match it came from, so it must be reversibly `sourceId|ruleId|identity` and nothing more (which is what makes "carries no lane, no shard" an enforced statement rather than a comment, and what rejects a fourth field such as `requiredLane`); distinct `(sourceId, ruleId, identity)` triples must yield distinct keys, so no segment can be silently dropped; and `Get-BackendTestShardPolicyIdentityMatches` is probed with selectors differing from a frozen identity only in case, which must not match, so the ordinal comparison cannot be relaxed to `OrdinalIgnoreCase` and silently widen every exclusion.

Timing keys get the corresponding treatment. The suite asserts that each assembly resolves to the same key and the same measurement before and after the rearrangement, and — on a synthetic lookup that prices every classified assembly distinctly, so the check never depends on how complete the committed snapshot is — that the moved assembly's milliseconds leave the donor shard's total and arrive in the receiver's, exactly. What it deliberately does **not** assert is that every assembly has a measurement: a coverage gap is `timing-assembly-missing`, it is report-only by construction, and gating on it would re-impose the human snapshot-refresh ceremony this issue removed. The gap count is printed for the job log instead.

The 17/64 lost keys are settled by this migration rather than by another refresh: with an assembly-only key there is nothing left for a shard rearrangement to invalidate, so the concept no longer exists and #1228 does not reopen.

### Lane is an applicability condition, not an identity key

`Test-NervRuleApplies` still reads `allowedLanes` and `requiredLane`, which looks at first glance like the coupling this section says was removed. It is not, and the distinction is the one worth writing down:

- An **identity key** answers "which row is this?". For timing that is the assembly; for policy it is the test full name plus the registering source path and ordinal. Nothing topological appears in either, which is why re-homing a project cannot invalidate a row.
- An **applicability condition** answers "does this rule have anything to say about the run in front of me?". A skip that is legal because PostgreSQL was not selected stops being legal the moment the PostgreSQL lane *is* selected. Lane is that condition, and deleting it would delete the third hard gate with it: `zero-execution` exists precisely to say that a selected real-dependency lane must actually have executed something.

The two never meet, because the lane that reaches the condition is the **logical** lane. `Test-NervRuleApplies` strips any `-shard-N` suffix (`^…-shard-[1-9][0-9]*$`) before it compares, so `backend`, `backend-shard-1` and `backend-shard-4` are one value by the time any matching happens, and the shard dimension is gone. A re-shard therefore cannot change a rule's verdict — asserted, not asserted-by-comment: `scripts/tests/backend-test-shards.Tests.ps1` evaluates every policy rule against each logical lane and against several shard spellings of it on both runner operating systems, and requires the verdicts to be identical.

The same suite also compares the three hard gates' verdicts across the simulated rearrangement itself, running the production engine (`Get-NervTestEvidenceViolations`) over synthetic runtime skips for the moved test identities under the donor lane and the receiver lane. Both sets are legitimately empty — a registered skip in an allowed lane is not a violation — so a third evaluation under a lane the rules do not allow is included as a control, and it must produce `unregistered-skip`; otherwise "identical verdicts" would just be two empty sets agreeing.

That fixture only ever emits `unregistered-skip`, so on its own it leaves the other two gates compared as empty against empty, which is not a test of them. Each gate therefore has its own live fixture, and each is asserted to be non-empty before its verdicts are compared:

- `illegal-quarantine` — a probe policy row classified `quarantined` with an expired `expiresOn`, evaluated under the donor lane and the receiver lane. Quarantine legality is read from the row's own metadata and touches no lane, so the two verdict sets must be identical; a second run of the same row with an unexpired date must produce nothing, which is what stops the fixture from passing on a gate that always fires.
- `zero-execution` — this gate speaks only about `realDependency: true` lanes, so it cannot be reached through the fast-shard lanes at all. It is exercised on the `postgres` lane instead, with the certifying work attributed to one fast shard and then to another: the verdict must not move. The controls are that a passed result *in* the selected lane clears the gate, and that the logical lane and several `-shard-N` spellings of it certify identically.

### One known report-only artefact

The assembly-keyed comparison has one residual case, recorded here rather than left to be rediscovered. When the committed snapshot holds a single row for an assembly under lane A, and the current run splits that assembly across lanes A and B, both current rows resolve to the same baseline row — so each is compared against the *whole* previous measurement and reports a delta that overstates the change. This is a display artefact of a genuinely ambiguous comparison, not a lost key, and it is report-only like every other delta: nothing gates on it and no gap it produces can turn a job red. The alternative — refusing to compare a split assembly at all — trades a slightly wrong number for no number, which is worse for the only thing the delta is for.

Summaries must also have unique valid lanes, the allowlisted lane-to-job mapping, successful native execution, nonzero execution, and no failures or violations. The production generator exposes no Actions-fixture or other authority replacement parameter. Both generator paths use the same checkout-provenance validator: it verifies push head/tested equality while preserving distinct PR head/tested values for validation, then independently enforces that only `main` push evidence is baseline-eligible. EvidenceRoot additionally verifies run URL/workflow/event/branch/head SHA/attempt/conclusion, the latest entry's matching ID/head SHA/attempt/conclusion/event/branch, every required job, and each job log's tested SHA, runner OS/image/version, and exact SDK. Tests exercise the pure validators with fixture objects. Rows are still *stored* per lane plus assembly, because a lane is real provenance for where a measurement was taken, but the reader's comparison key is the assembly alone (see "Timing data is a cache, not a governed asset"), and timing deltas are emitted only when both sides use TRX elapsed timing at test granularity. Commit the script-generated diff with its per-lane resolved runner image and actual .NET SDK provenance; never hand-edit the snapshot.

### Run identity versus per-job environment

The eleven provenance fields on an evidence summary were originally checked as one set: complete, nonempty, and byte-for-byte equal across every lane. Eight of them earn that. `workflowRunId`, `runAttempt`, `headSha`, `testedSha`, `repository`, `event`, `headBranch` and `sourceUrl` are properties of **the run**, and every job of one run reports the same values by construction — so an inequality there is not a runner quirk, it means two different runs were mixed into one baseline. Equality on those eight is a real check and is unchanged.

The other three — `runnerOs`, `runnerImage`, `dotnetSdk` — are properties of **the machine one job landed on**. GitHub schedules each job independently, so "this run's runner image" is not a thing that exists. The equality rule held only while the hosted fleet happened to be homogeneous. On 2026-08-07, mid image rollout, two consecutive qualifying `main` push runs each spanned two images in a *different* per-lane mix:

| Run | `backend-shard-1` | `backend-shard-2` | `backend-shard-3` | `backend-shard-4` | `connector-host` |
| --- | --- | --- | --- | --- | --- |
| `31149427664` (`b490ca8d4`) | `…20260720.247.2` | `…20260804.265.1` | `…20260720.247.2` | `…20260804.265.1` | `…20260804.265.1` |
| `31161226667` (`c74f633d5`) | `…20260720.247.2` | `…20260720.247.2` | `…20260720.247.2` | `…20260804.265.1` | `…20260720.247.2` |

Both are legitimate. Under the old rule both failed with `Evidence summaries have mixed provenance field 'runnerImage'`, which blocked baseline refresh outright: `Assert-NervEvidenceRootAuthority` also requires the source to be the *latest* qualifying run, so the only way through was to win a race — wait for a run whose five jobs happened to land on one image, then consume it before the next `main` push landed. If a fraction `p` of the fleet carries the new image and jobs are scheduled independently, the chance all five lanes match is `p⁵ + (1−p)⁵`: about 6% at `p = 0.5`, rising toward 1 only as the rollout finishes. That is a schema limitation wearing a validation costume: `source` was flat, so it could not express "five lanes, two images", and the equality rule was what kept the flat shape from producing a false record.

The fix is to let the schema say what is true. **Baseline `schemaVersion` is now 2**: `source.runnerOs` / `source.runnerImage` / `source.dotnetSdk` are gone, replaced by `source.laneProvenance` — one row per evidence lane carrying that lane's `jobName`, `runnerOs`, `runnerImage` and `dotnetSdk`. There is no run-wide runner field left for a reader to mistake for the whole. A **schema-1** baseline's flat trio is the *first lane's* environment and must never be read as run-wide; the committed baseline was schema 1 until the 2026-08-07 refresh and has been schema 2 since (currently run `31185687984`).

That distinction is enforced, not merely documented. `New-NervTestEvidenceSummary` accepts only `schemaVersion` 1 or 2 and reports `unsupported-baseline-schema-version` for anything else — comparison then degrades to report-only unavailable instead of running against a layout this code has never seen. Both known versions compare identically, because the comparison key is the assembly and no lane or runner field participates; the guard exists so that a *future* third shape cannot be read as if it were one of these two. **This paragraph is the single authority for the schema-version guard's rationale.** The code and its contract tests carry a one-line conclusion plus a pointer here; if the guard changes, this is the place to edit.

"Anything else" is literal, and covers every shape a JSON file can actually hold: an absent `schemaVersion`, `null`, a non-numeric string, a boolean, an array, a fractional number. The version is read with `[int]::TryParse` rather than an `[int]` cast for exactly that reason. The cast did three different wrong things: it raised a conversion error out of a pure summary builder for `"abc"` and `[1, 2]` (a different failure from the structured reason this paragraph promises), it silently *rounded* `1.5` into the supported set, and it turned `true` into `1` so a boolean was compared as if the file had said schema 1 — the last one produced a real signed delta against a layout that had never been read.

Contract tests cover six non-integer shapes behaviourally — asserting the reported reason, that the reason reaches every assembly row, and that nothing throws. Four of the six are guards that go red if the TryParse is reverted: `"abc"`, `[1, 2]`, `1.5`, `true`. The other two, `null` and an absent field, reject identically under both spellings (`[int]$null` was already `0`); they are shape coverage and must not be counted as evidence for this fix.

`TryParse` is called without a `NumberStyles`/`IFormatProvider` argument, unlike the `[DateTimeOffset]::TryParse(..., InvariantCulture, ...)` elsewhere in the same file. That asymmetry is deliberate and the two cases are not alike: the date strings there arrive as external text that genuinely *is* culture-formatted, whereas the value here has already passed through PowerShell's `[string]` cast, which renders numerics invariantly. **Over the shapes this guard actually receives — every value that reaches it through the `[string]` cast — its verdict is culture-invariant, and no regression test asserts it, because over those shapes such a test could not fail.** That was measured rather than assumed: 11 JSON-representable values × 5 cultures (`en-US`, `de-DE`, `fr-FR`, `zh-CN`, `ar-SA`) × 3 plausible guard spellings (current-culture `Integer`, invariant `Integer`, current-culture `Number` with thousands separators) = 165 combinations, with **zero** verdict differences across cultures, zero across guard spellings, and zero culture-dependent `[string]` renderings.

That claim is bounded, and the bound is load-bearing: a case *can* be constructed that distinguishes the two spellings. Give `schemaVersion` a JSON **string** whose text is the current culture's own `PositiveSign` followed by `2` — codepoints `U+061C U+002B U+0032` under `ar-SA`/`ar-EG`, `U+200E U+002B U+0032` under `fa`/`fa-AF`/`fa-IR`, `U+200F U+002B U+0032` under `ckb-*` (written as codepoints here on purpose; the literals are invisible bidi marks). The `[string]` cast is then the identity, the original text reaches `TryParse` unchanged, and current culture **accepts** it as `2` where the invariant overload **rejects** it. Measured on this repo's .NET/ICU: 63 of 1063 cultures carry a non-ASCII `PositiveSign`, in four distinct spellings; a test asserting rejection under `ar-SA` goes red on today's code and green on an invariant one, so it is discriminating, not a tautology.

**It is still deliberately not added, and the guard is still deliberately left as-is.** What such a test would pin is an incidental tolerance for an exotic sign, not this guard's contract; and when the sign *is* tolerated, the value that comes out is the correct `2` — unlike the `true → 1` shape above, nothing then runs a full comparison against a layout it never read. Note also that culture has exactly one *reachable* door into this guard, and it is the sign. The other candidate surface does exist in the culture data — of those same 1063 cultures, **92 do declare** a non-ASCII `NumberFormat.NativeDigits[0]` (Arabic-Indic `U+0660`, extended Arabic-Indic `U+06F0`, Devanagari `U+0966`, Bengali `U+09E6`, N'Ko, Tibetan, Burmese, Adlam, and three more, 11 distinct digit sets in all) — but `[int]::TryParse` accepts none of them under any culture, including that culture's own: `U+0662` parses as `False`, and feeding every one of those 92 cultures its own native `2` while it is the current culture yields zero acceptances. The native-digit surface is present in the data and simply unreachable through this guard, so the sign remains the only door — and the sign is reachable only by text that bypasses the `[string]` cast.

**Both counts above are ordinal** (`[string]::Equals(…, StringComparison::Ordinal)`), and that qualifier is the whole reason they are trustworthy: every number in this paragraph was first got wrong by comparing culture-aware instead. PowerShell's string comparison is culture-aware by default, and the `c` prefix does **not** make it ordinal — `-eq`/`-ne` and `-ceq`/`-cne` alike consult the collation table, which reports "same" for exactly the characters at issue here. The bidi marks in the signs are collation-ignorable (`"$([char]0x061C)+" -eq '+'` returns `$true`, and `-cne` likewise returns `$false`), and each native digit set sorts equal to its ASCII counterpart (`"$([char]0x0660)" -ne '0'` returns `$false`, though the two are different characters). Over identical data the identical scan reports:

| written as | non-ASCII `PositiveSign` | non-`'0'` `NativeDigits[0]` |
| --- | --- | --- |
| ordinal | **63** | **92** |
| `-ne` | 0 | 0 |
| `-cne` | 0 | 0 |

**`Group-Object` is the same trap in a worse form, because it is implicit and silent.** Its default key comparison is culture-aware too, so grouping those 92 cultures by their raw `NativeDigits[0]` string yields **one** group of 92 — all eleven digit sets folded together, with no error and no warning. Keying on the codepoint instead (`[Text.Rune]::GetRuneAt(…).Value`) yields the **11** groups reported above; the sign side collapses identically, 4 spellings into 1. So it is possible to filter entirely with ordinal comparisons, get the 92 right, and still lose the whole distribution at the final grouping step. Anyone re-running this matrix must compare **and key** ordinally, or they will be measuring the collation table rather than the culture data.

The measurement is a one-off, so treat it as an argument for why the question is closed, not as a live guard: if a future edit gives this guard a culture-sensitive `NumberStyles` (`AllowThousands`, `AllowDecimalPoint`) or moves the value in as raw text instead of through the `[string]` cast, re-run that matrix rather than trusting this paragraph. The counterexample above lands squarely on the second trigger, which is the evidence that the trigger is watching the right seam.

`source.laneProvenance` is also required to be **complete**. Its lane set must equal, exactly and in both directions, the lane set the baseline's assembly rows record: no missing lane, no stray lane, no duplicate lane. A partial `laneProvenance` would be strictly worse than the flat trio it replaced — the flat field at least announced itself as run-wide, whereas one row sitting beside five lanes of timing is a silent partial record that reads as complete, which is the exact failure this split exists to prevent. Each row's `jobName` is provenance too and is checked against the same `Get-NervTestEvidenceLaneJobs` allowlist that binds summaries: for an allowlisted lane the job name must match exactly, so a row cannot be blank, invented, or borrowed from a sibling lane. (A lane outside that allowlist — only the legacy console import's unsharded `backend`, which the allowlist deliberately omits — still has to name some job.)

**What was traded away, precisely:** cross-lane equality of `runnerOs`. Two lanes of one baseline may now report different operating systems at the summaries gate, where previously they could not. Nothing else changed hands — `runnerImage` and `dotnetSdk` never had a per-lane-only compensating check to lose, and every per-summary shape rule was kept and one was added. Three things cover the `runnerOs` case: the value must now match the `Linux`/`Windows`/`macOS` enum (previously it only had to be nonempty); `Assert-NervEvidenceRootAuthority` derives each lane's OS from **that lane's own job log** and rejects a mismatch; and today all five CI-wired lanes run on `ubuntu-24.04`, so a genuine cross-OS baseline would be a deliberate topology change, not a drift.

Per-summary shape validation is otherwise unchanged: the image must be a resolved `<image>@<version>` (never a selector such as `ubuntu-latest`) and the SDK must be an exact three-part version. More importantly, the check that actually protects the environment record was never the cross-lane comparison — it is `Assert-NervEvidenceRootAuthority`, which downloads **each lane's own job log** and requires that lane's summary to match the image, OS and SDK it independently resolves from that log. That is strictly stronger than cross-lane equality: it rejects a lane that borrows a sibling lane's genuinely-present image, which equality by definition could not. Contract tests cover the accepted mixed-image run, per-field rejection of mixed run identity, per-lane recording in the baseline, the missing/stray/duplicate lane and blank/invented/borrowed `jobName` cases, the schema-version guard, and the swapped/forged single-lane authority cases.

The Script Governance CI job and `check-script-compatibility.ps1 -FastOnly` both execute `scripts/tests/test-evidence.Tests.ps1` directly, so semantic contract failures propagate their actual process exit code instead of relying on source scanning. `summary.json` and Job Summary expose the same selected lane selectors and logical result rows.

Successful retained artifacts intentionally replace a failed test's raw message with a bounded privacy-safe placeholder and keep `diagnostics.log` empty; the failure root remains in the access-controlled Actions job log. This is a deliberate privacy boundary, not a claim that retained artifacts contain full failure diagnostics.

Local fixture results, local full solution execution, PR CI and artifact availability, merge status, actual real-dependency lane execution, and post-merge test-granularity baseline refresh are separate delivery states. None implies another.
