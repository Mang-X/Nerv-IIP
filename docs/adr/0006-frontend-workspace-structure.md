# ADR 0006：前端工作区与目录边界

- 状态：已接受
- 日期：2026-05-13

## 背景

Nerv-IIP 前端既要保留工程边界，又要适合 AI 协作与持续代码生成。平台会同时包含可运行应用、生成契约、通用 UI 与跨应用能力，单一 `src` 无法稳定承载这些职责。

团队接受 Nuxt 风格的显式目录语义，但不接受 Nuxt 式运行时约束或过强的隐式魔法。Vite+ 已覆盖格式化、检查与任务编排的默认需求，前端不再默认叠加 ESLint、Prettier、Turborepo。根级工作区规则与应用级 Vue 运行时配置必须分离，否则职责会持续耦合。

具体 app/package 名单、目录树、职责与依赖方向会随平台演进，属于 Current Architecture，不应在 ADR 中维护第二份快照。

## 决策

1. 前端采用 pnpm 工作区，以 `apps/*` 表达独立可运行入口，以 `packages/*` 表达有真实跨应用复用价值的稳定能力。
2. 根级配置只负责工作区成员、共享 TypeScript/Vite+ 基线、聚合任务和共享检查规则；应用级配置负责 Vue、Router、alias、构建及应用私有类型；包级配置负责稳定导出、生成器和自身测试边界。
3. 应用采用显式 Vue 目录与入口，不引入 Nuxt 式运行时约束或依赖隐式目录魔法完成关键装配。
4. 页面或应用私有目录不得充当跨应用事实共享层。能力只有在出现真实跨应用复用压力后才上提到 `packages/*`。
5. 生成代码与手写代码必须隔离。应用只通过生成包的稳定导出消费契约，不在页面、API 组装层或共享包中复制生成 DTO。
6. 默认不要求额外的 `src/app` 启动引导层；只有入口装配复杂度明显升高、且职责可被清晰命名时才引入。
7. 当前 app/package 清单、目录结构、职责、依赖方向和配置落点只在 [`../architecture/frontend/workspace-structure.md`](../architecture/frontend/workspace-structure.md) 维护；本 ADR 只保留上述长期边界及其理由。

## 理由

1. 显式入口与稳定边界比抽象完整更适合当前阶段，也更利于人和 Agent 正确定位修改位置。
2. 根级、应用级和包级配置分层后，工作区规则不会污染单应用运行时配置，新增应用或包时也不需要重构根配置职责。
3. 共享包边界按真实复用压力建立，可以避免某个控制台应用或页面目录演化成新的大一统代码仓，也避免提前制造空壳公共包。
4. 不强制 `src/app` 可以降低样板复杂度，同时保留入口层变重后再抽离的空间。
5. 生成产物通过稳定 package 导出，可以把接口变化的影响限定在明确消费边界内，避免生成与手写代码互相覆盖。
6. 将现态目录树交给 Architecture 单点维护，可以让 ADR 保持历史理由，同时避免每次新增 app/package 都修改决策记录。

## 已考虑的替代方案

1. **单一 `src` 目录承载全部前端职责。** 否决。可运行应用、生成契约、通用 UI 和跨应用能力具有不同发布与依赖边界，放入单一目录会让复用和所有权逐渐隐式化。
2. **采用 Nuxt 式运行时约束。** 否决。团队需要其清晰目录语义，但不需要框架运行时约束和关键装配的隐式魔法。
3. **在 Vite+ 之上默认叠加 ESLint、Prettier、Turborepo。** 否决。现阶段会形成重复配置与任务来源；新增工具必须由独立需求证明 Vite+ 无法承担的能力。
4. **默认创建 `src/app` 作为启动引导层。** 暂不采用。没有真实复杂度时会增加样板和定位层级；出现清晰、稳定的启动职责后再引入。
5. **在 ADR 中冻结完整 app/package 名单与目录树。** 否决。该信息随实现持续变化，应由 Current Architecture 和仓库结构维护；复制到 ADR 会形成双重架构事实。

## 后果

1. 前端仓库比单应用模板多出 workspace、apps 与 packages 分层，初始化与依赖治理成本更高。
2. 团队需要持续判断能力是应用内共享还是跨应用稳定边界，不能仅为了“以后可能复用”上提 package。
3. 根级脚本、应用脚本和包脚本会同时存在；当前命令必须由 package scripts、配置、帮助与 Runbook 维护。
4. 新增 app/package 通常只更新 Current Architecture 和实现；只有工作区模型、配置职责、复用门槛或生成隔离原则改变时，才需要新 ADR 取代或修订本记录。

## 实施说明

1. 当前工作区成员、职责、依赖方向、配置分层和路由/状态/API 组织见 [`../architecture/frontend/workspace-structure.md`](../architecture/frontend/workspace-structure.md)。
2. 精确命令、版本、workspace 成员与构建配置以 `frontend/package.json`、`pnpm-workspace.yaml`、各 app/package 的 `package.json`、Vite 配置和相应 Runbook 为准。
3. 当前完成度、迁移缺口和验证证据以关联 Issue、PR 与 CI 为准；本 ADR 不追加实施状态日志。

## 复评触发条件

出现以下任一变化时，应通过新 ADR 复评本记录：

1. 放弃 pnpm apps/packages 工作区模型；
2. 根级工作区配置与应用运行时配置不再分层；
3. 引入依赖隐式目录魔法的前端运行时框架；
4. 允许 app 私有目录成为跨应用共享边界；
5. 生成代码与手写代码不再隔离。

## 范围之外

1. 不在本 ADR 中决定视觉设计系统细节或具体 UI 组件库。
2. 不在本 ADR 中冻结任何应用或 package 的数量、名称、目录树、端口、命令、依赖版本或交付状态。
