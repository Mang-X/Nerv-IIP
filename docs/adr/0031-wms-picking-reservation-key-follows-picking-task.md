# ADR 0031：WMS 拣货预留幂等键按拣货任务区分

- 状态：已接受
- 日期：2026-09-27

## 背景

[ADR 0019](0019-wms-inventory-rpc-idempotency.md) 决策第 1 条把拣货预留的幂等键定为 `wms-pick-res:<hash(organizationId:environmentId:outboundOrderNo:lineNo)>`，并规定同键同载荷的重试返回既有预留。键只跟随出库单行，不区分这一行上先后建立的拣货任务。

#3836 调查发现这会把一次新的业务请求误当成旧请求的重放：拣货任务建立后，预留在开拣前超时过期，WMS 取消该任务并清掉该行的预留引用；之后为同一行重建拣货任务时，键不变，Inventory 按 ADR 0019 把那份已过期的旧预留原样返回。WMS 把它当成有效预留挂到新任务上，直到出库过账核销时才被拒绝，这一行此后无法再走通。

超时恢复（ADR 0019 要解决的问题）与任务作废后重建是两种不同的意图：前者是同一个业务操作在重试，后者是一个新的业务操作。键必须能区分二者。

## 决策

1. 拣货预留的幂等键在 ADR 0019 的业务身份之外，再加入拣货任务的持久标识：`wms-pick-res:<hash(organizationId:environmentId:outboundOrderNo:lineNo:taskNo)>`。任务号在组织与环境内唯一，且由创建拣货任务的命令携带，同一条命令重试时保持不变。
2. 同一拣货任务的重试（包括 Inventory 已提交、WMS 超时后的重放）仍按 ADR 0019 返回既有预留。
3. 拣货任务作废后，以新任务号重建是新的业务请求，得到新的预留；已失效的旧预留不会被重放给新任务。
4. 本记录只部分修订 ADR 0019 决策第 1 条的拣货预留键公式。ADR 0019 的盘点冻结键、Inventory 侧“相同键 + 相同载荷返回既有结果 / 相同键 + 不同载荷拒绝”的语义、超时恢复方式与并发不变量仍然有效。

## 理由

主流 WMS 的预留或分配跟随拣货任务 / 转储单（例如 SAP 的 transfer order），而不是跟随出库单行：任务作废后重新下达任务，就重新分配库存。把预留身份绑在任务上，与仓库作业的实际粒度一致。

任务号本身就是持久、稳定的业务身份，满足 ADR 0019 对“从稳定业务身份派生、不使用一次调用的临时 ID”的要求。超时恢复场景重试的是同一条命令、同一个任务号，恢复语义不受影响。

## 实施说明

1. 精确键格式是代码契约，以 WMS 的预留幂等键实现为准；当前架构说明见 [`../architecture/business/wms-inventory-rpc-idempotency.md`](../architecture/business/wms-inventory-rpc-idempotency.md)。
2. ADR 0019 通过头部修订依据和实施说明链接本记录；其决策第 1 条原文不原地改写。

## 已考虑的替代方案

1. **保持键不变，Inventory 在重放时拒绝非 open 的预留。** 否决。它同样推翻 ADR 0019 “相同键返回既有结果”的语义，且拒绝之后 WMS 仍无法为这一行重新预留，只是把卡住的位置提前。
2. **保持键不变，WMS 在预留失效时为行维护一个递增代次并编入键。** 否决。代次是 WMS 自造的计数，不是业务身份；任务号已经能表达“这是哪一次拣货请求”，不需要另起一套身份。
3. **每次调用生成新的随机键。** 否决。会让超时重试产生第二份预留，违背 ADR 0019 的超时恢复目标。

## 后果

1. 同一出库单行上，每个拣货任务对应自己的预留身份；重建任务不会再拿回已失效的预留。
2. 部署切换时，若某条创建拣货任务的命令恰在旧版本下超时、在新版本下重试，会按新键得到第二份预留；旧预留随超时自然回收。这是一次性的切换窗口，不做迁移处理。
3. 盘点冻结链路不受影响。

## 范围之外

1. 预留在拣货完成后保持到出库过账、以及 Inventory 释放的幂等语义，属于同一 Issue 的实现改动，不是本记录的决策内容。
2. 拣货任务号目前由操作者填写、没有编码规则，是独立的产品缺口，不在本记录裁决。
