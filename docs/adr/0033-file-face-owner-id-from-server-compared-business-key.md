# ADR 0033：文件门面的 owner 标识可取自服务端逐字比对的业务键

- 状态：已接受
- 日期：2026-09-30
- 部分修订：[ADR 0030](0030-business-gateway-purpose-scoped-file-transfer.md) 决策 2 中「业务侧每条文件门面固定一个 `filePurpose` 与 owner，不从请求体读取」对 **owner 标识**的适用性；用途与 owner 服务、owner 类型仍由网关固定，ADR 0030 其余条款仍有效。
- 关联：[Issue #3856](https://github.com/Mang-X/Nerv-IIP/issues/3856)

## 背景

ADR 0030 决策 2 规定，业务侧每条文件门面固定一个 `filePurpose` 与 owner，不从请求体读取。已有的两条门面满足这一条：工程 SOP 文件只下载；交接班附件的 owner 标识取认证 principal，由网关决定。

#3856 要在控制台为条码模板开上传门面。BarcodeLabel 在建打印批次时按 Ordinal 逐字比对模板文件的 owner 标识与已存模板编码（`HttpFileStorageLabelTemplateAssetAdapter`），不一致就拒绝，所以这条门面的 owner 标识只能是模板编码。

问题在于上传发生时服务端还没有这条模板记录。条码模板在命令校验、领域对象、数据库列三层都要求模板文件必填，用户只能「先上传文件、再保存模板」。上传那一刻，网关找不到任何服务端记录可以拿来当 owner 标识，模板编码只能由请求带进来。

## 决策

1. 用途、owner 服务、owner 类型仍由网关固定，不从请求体读取。本条不改变 ADR 0030 决策 2 对这三项的要求。
2. owner 标识可以取自请求中的业务键，但必须同时满足两个条件：
   - **服务端逐字比对**：使用方在使用该文件时，会把文件的 owner 标识与服务端已存的同一业务键逐字比对，绑错的文件在使用时被拒；
   - **不因此越权**：持有该门面写权限的主体，本来就能修改该业务键下的资源。
   两个条件缺一，owner 标识仍须由网关依据服务端事实或认证身份决定。
3. 网关对取自请求的业务键只做与使用方存储时相同的规范化（例如去掉首尾空白），不做其它改写，保证与使用方比对的是同一个值。
4. 首个适用实例是 `barcode-template-assets`（BusinessGateway 条码模板文件上传门面）：
   - owner 服务、类型固定为 `business-barcode-label` / `label-template`；
   - owner 标识取请求中的模板编码（Trim 之后）；
   - 使用方 BarcodeLabel 建打印批次时按 Ordinal 比对模板编码，满足条件一；
   - 门面权限 `business.barcodes.templates.manage` 本就能创建和修改任意模板及其文件，满足条件二。

## 理由

- owner 在这类门面上的作用，是保证文件只能被它所属的业务对象使用。只要使用方在使用时逐字比对，调用方绑错只会让文件用不上，不会让文件被别的对象误用；所以「谁写入 owner 标识」对这个保证不承重，承重的是使用方的比对。
- 条件二排除了越权面：如果写权限本就覆盖该业务键下的全部资源，那么让调用方自报业务键，并不会让他获得原本没有的能力。
- 条码模板的「文件必填」三层约束形成了「先上传、再建模板」的次序，上传时服务端没有记录。在不改变这一次序的前提下，没有其它服务端事实可以充当 owner 标识。

## 已考虑的替代方案

1. **模板改为可以没有文件，先保存模板、再按已存记录上传。** 拒绝。它要求 BarcodeLabel 在命令、领域、数据库三层放开必填，改列并补迁移，所有使用模板文件的链路（建打印批次、资产退役、历史种子校验）都要处理「没有文件」这一态。另外 BarcodeLabel 目前没有按 id 读取模板的接口，还要新增下游接口。为了让 owner 来源形式上满足 ADR 0030，要付出跨服务改动和一个原本不存在的业务状态，代价与收益不相称。
2. **照交接班附件的做法，owner 标识绑定上传者。** 拒绝。BarcodeLabel 打印时要求 owner 标识等于模板编码，资产退役的证明也以模板编码作为 owner 标识。绑上传者会让文件在打印时一律被拒；若改成放开使用方的比对，就等于拆掉条件一所依赖的那道校验。

## 后果

1. ADR 0030 决策 2 对 owner 的要求变成两层：用途、owner 服务、owner 类型必须由网关固定；owner 标识在满足本 ADR 两个条件时可以取自请求中的业务键。
2. 新开文件门面若要让 owner 标识取自请求，必须同时点名使用方的逐字比对点和权限覆盖依据；只满足其一，不适用本 ADR。
3. 调用方绑错业务键的失败要到使用时才出现（条码模板是建打印批次时被拒），而不是在上传时出现。门面的调用方应尽量让上传时的业务键与最终保存的业务键一致：条码模板弹窗在上传进行中锁住模板编码，并在上传完成时再核对一次。
4. FileStorage 侧不记录上传者身份。需要按人追溯上传行为时另行评估，不在本 ADR 范围内。

## 复评触发条件

- 使用方取消或放宽对 owner 标识的逐字比对；
- 门面写权限的覆盖范围收窄到业务键以下（例如按单个模板、按产线授权）；
- 条码模板不再要求文件必填，或 BarcodeLabel 提供按 id 读取模板的接口，使上传可以挂在已存记录上；
- 出现第二个想援引本 ADR 的门面时，逐条核对两个条件，不按「已有先例」直接套用。
