# Flow: Carried-Context Entry（带出式录入）

一线在**已选中的某一行**上继续干活的写弹窗（报工、完工入库、收货、上架、检验录入、
处置、派工…）。与 `create-dialog.md`（从零建档）互补：这里的对象**已经确定**，用户要补的
只是"这一次干了多少 / 结果如何"。

Owner 原话（报工，本流的定名场景）：

> 从工单或工序任务进入报工，系统带出必要字段，一线人员只补充数量和完成状态。
> 工单与工序来自所选行，只能从工单列表或工序任务带入。

## 规则

1. **入口只在行上**。没有页面级「新建 X」按钮凭空开这个弹窗；上下文为空即不渲染表单、
   不可提交。跨页跳转带两个裸 ID 不算"带出"——那会把工作中心 / 物料 / 计划数量全丢掉，
   应该把同一个弹窗组件挂到每个来源页上，就地打开。
2. **带出的字段只读展示，不做 `readonly` 输入框**。用
   `components/business/CarriedContextSummary.vue`（muted 卡片 + `<dl>`），与录入区在视觉上
   分层。`readonly` 的 `NvInput` 看起来仍是输入位，一线会去点、去改、去疑惑。
3. **录入项只保留真正的新决策**。能推出来的一律不问：时间取当前时刻，数量默认取上下文
   建议值，唯一候选的下拉自动选中。每砍掉一个录入项都要能说清"这个值从哪来"。
4. **零说明文案**。弹窗里不写"本弹窗用于…"、"系统会…"、"后端将…"、"必须为非负数"。
   对象是什么，只读区已经写着了。`NvDialogDescription` 不能整个删（reka-ui 会告警缺
   description），改成 `class="sr-only"` 的一行对象标识即可。
5. **结果一律 toast**，成功即关弹窗；字段校验点提交才标红且不发请求
   （见 `../feedback-and-notifications.md`）。
6. **带不出来就登记缺口**，不退化成手填、也不临时加一次取数。缺的读面字段进模块文档的
   「后端缺口」并发 consolidated issue。

## 判定

- 「这个弹窗能不能从空白页面打开？」能 → 打回（上下文必须来自行）。
- 「界面上有几个 `readonly` 输入框？」>0 → 打回（改只读区）。
- 「一线在这里做的决策有几个？录入项有几个？」录入项 > 决策数 → 打回。
- 「删掉所有说明文字，用户还知道自己在给哪张单报数吗？」不知道 → 只读区没写全，而不是
  需要说明文字。

## 正例

`apps/business-console/src/components/mes/ProductionReportDialog.vue`
（+ `composables/mes/useProductionReportForm.ts`）：工单 / 工序 / 工作中心 / 物料 /
计划数量全部只读带出，录入项只有合格数量、不合格数量、本工序是否完成；报工时间提交时取
当前时刻。三个来源页（工单列表行、工序执行行、报工记录「重新报工」）挂的是同一个组件。

## 反例

❌ **只读输入框冒充带出** —— 旧版报工弹窗把工单号 / 工序任务做成 `readonly NvInput`，
外加一行「工单与工序来自所选行，只能从工单列表或工序任务带入。」的说明框——既占了输入位的
视觉权重，又要用文字解释自己。

❌ **跨页跳转当带出** —— 工序执行页点「报工」跳到 `/mes/work-orders?workOrderId=…&
operationTaskId=…`，落地后只剩两个 ID，工作中心 / 物料 / 计划数量全丢，用户还得自己回头核对。
